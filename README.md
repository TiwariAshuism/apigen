# apigen

A type-safe, YAML-free Go API generator. Define a Go `interface` with HTTP annotations in comments — `apigen` reads it via `go/ast` and emits a fully wired **Handler + Service + Repository** stack.

```
You define → Go interface → apigen parses AST → outputs MVC stack
```

---

## Quick Start

```go
// api/routes.go
//go:generate go run ../../cmd/apigen -input routes.go -output ..

type UserAPI interface {
    // GET /users
    ListUsers(ctx context.Context, req ListUsersRequest) ([]User, error)
    // GET /users/:id
    GetUser(ctx context.Context, id string) (User, error)
    // POST /users
    CreateUser(ctx context.Context, req CreateUserRequest) (User, error)
    // PUT /users/:id
    UpdateUser(ctx context.Context, id string, req UpdateUserRequest) (User, error)
    // DELETE /users/:id
    DeleteUser(ctx context.Context, id string) (User, error)
}
```

```sh
go generate ./api/...
```

Generates:

| File | Contents |
|---|---|
| `internal/handler/user_handler_gen.go` | Gin routes, JSON binding, calls service |
| `internal/service/user_service_gen.go` | `UserService` interface |
| `internal/repository/user_repository_gen.go` | `UserRepository` interface |

## Installation

To use `apigen` as a CLI tool in your projects:

```sh
go install github.com/user/apigen/cmd/apigen@latest
```

Or run directly from source within this repo:

```sh
go run ./cmd/apigen [flags]
```

---

## Usage

```
apigen [flags]

Flags:
  -input    string   Path to a Go file or directory containing interface definitions
                     (default "api/routes.go")
  -output   string   Root output directory (default ".")
  -module   string   Go module path — auto-detected from go.mod if not set
  -layers   string   Comma-separated layers to generate (default: all)
                     Choices: handler, service, repository, openapi
  -dry-run           Print what would be generated without writing any files
```

### Examples

```sh
# Standard: auto-detects module, generates all 3 layers
apigen -input api/routes.go -output .

# Generate only the service interface
apigen -input api/routes.go -output . -layers service

# Generate an OpenAPI 3.0 spec alongside the MVC layers
apigen -input api/routes.go -output . -layers handler,service,repository,openapi

# Preview output without writing (useful in CI)
apigen -input api/routes.go -output . -dry-run

# Parse an entire directory of interface files
apigen -input api/ -output .
```

## Interface Annotation Format

HTTP metadata is declared in the **doc comment** immediately above each method:

```go
type OrderAPI interface {
    // GET /orders
    ListOrders(ctx context.Context, req ListOrdersRequest) ([]Order, error)

    // GET /orders/:id
    GetOrder(ctx context.Context, id string) (Order, error)

    // POST /orders
    CreateOrder(ctx context.Context, req CreateOrderRequest) (Order, error)

    // PUT /orders/:id
    UpdateOrder(ctx context.Context, id string, req UpdateOrderRequest) (Order, error)

    // DELETE /orders/:id
    DeleteOrder(ctx context.Context, id string) (Order, error)
}
```

**Rules:**
- Comment format: `// <VERB> <path>` (verbs: `GET POST PUT DELETE PATCH`)
- Path params use `:name` syntax — they must match a `string` parameter in the signature
- The first parameter must be `context.Context`
- Methods without an HTTP comment are **skipped** with a warning

## How It Works

1. **Parser** (`internal/parser`) — uses `go/ast` to walk interface types, extract method signatures, and parse HTTP annotations from doc comments. Accepts a single file or a whole directory.

2. **IR** (`internal/model`) — a simple intermediate representation: `APIDefinition → []Method → Param`. No YAML, no reflection.

3. **Generator** (`internal/generator`) — renders three `text/template` files embedded into the binary via `//go:embed`. Runs `go/format` on all `.go` output. Skips unchanged files.

4. **CLI** (`cmd/apigen`) — thin wrapper: parse flags → call parser → call generator.

## Generated File Layout

```
your-project/
└── internal/
    ├── handler/
    │   └── <resource>_handler_gen.go   ← Gin handler, route registration
    ├── service/
    │   └── <resource>_service_gen.go   ← Service interface (implement separately)
    └── repository/
        └── <resource>_repository_gen.go ← Repository interface (implement separately)
```

Generated files carry `// Code generated by apigen. DO NOT EDIT.` and use the `_gen.go` suffix so linters and editors treat them correctly.

---

## Implementing the Generated Interfaces

Generated files contain **only interfaces** — safe to regenerate at any time. Write your implementations in separate files:

```
internal/service/
  user_service_gen.go      ← GENERATED — interface only, do not edit
  user_service_impl.go     ← YOURS — business logic, edit freely

internal/repository/
  user_repository_gen.go   ← GENERATED — interface only, do not edit
  user_repository_impl.go  ← YOURS — DB queries, edit freely
```

When you add a method to the interface and re-run `go generate`, only the `_gen.go` file updates. The Go compiler will immediately tell you which new methods to add to your impl.

## OpenAPI Output

Pass `-layers openapi` (or include it in a comma-separated list) to emit an OpenAPI 3.0 YAML spec alongside the Go files:

```sh
apigen -input api/routes.go -output . -layers handler,service,repository,openapi
```

Output: `internal/<resource>_openapi.yaml`

## How to use in your own project

1.  **Install the tool** as shown in the Installation section.
2.  **Define your API interface** in a Go file (e.g., `api/routes.go`). Use HTTP annotations in comments.
3.  **Ensure you have a `go.mod` file** in your project root or a parent directory. `apigen` uses this to detect your module path for imports.
4.  **Run the generator**:
    ```sh
    apigen -input api/routes.go -output .
    ```
5.  **Project Layout Requirement**: `apigen` expects to generate code into an `internal/` directory at your `-output` path. It will create:
    -   `internal/handler/`
    -   `internal/service/`
    -   `internal/repository/`
    -   `internal/model/` (Note: You should define your shared structs here or ensure they are accessible).

## Design Decisions

**Why comments for HTTP metadata?**  
Comments are valid Go — no build-time cost, IDE-visible, zero reflection. The interface file remains compilable and type-checked by the Go toolchain.

**Why `go/ast` over reflection?**  
AST runs at codegen time on source. It works on interfaces (not just concrete types), sees parameter names, and has zero runtime overhead.

**Why interfaces-only in generated files?**  
Implementations written in separate files survive regeneration. The compiler enforces the contract — if a new method is added to the interface, the missing method error points directly to the impl file.

**Why `embed.FS` for templates?**  
The binary is self-contained. Templates are not resolved relative to the working directory, so `apigen` works correctly regardless of where it is invoked.
